# How NDT works

> This document provides a concise overview of how ndt7
> works that recaps the main design decisions, summarizes
> the empirically known design and implementation
> concerns, and generally provides the basic information
> necessary to understand the work carried out in this
> repository.

The current version of the NDT protocol is 7. The protocol
itself is called `ndt7`. This document explains how it should
work.

The general idea around `ndt7` is to perform a 10 second
download data transfer and a 10 second upload data transfer to
measure the bulk transport rate in both directions. The
early-exit mechanism allows servers to interrupt the download
test earlier when they determine that the performance has
stabilized. However, we do not consider early-exit for
the purposes of this investigation, because we focus on
`giga-meter`, which does not request this feature.

We use a single connection because that allows us to collect
kernel-level quality metrics such as TCPInfo and keep them
interpretable. A single connection means a single congestion
control algorithm facing the confounding factors present in
the network. Multiple connections would also compete with
each other, adding self-inflicted confounding to each
connection's metrics.

We use TLS by default since the web uses TLS by default and
we aim to measure the experience of connections using the web.

When designing the ndt7 protocol, the theory guiding us was that
a single WebSocket connection would approximate well-enough the
behavior of a raw TLS connection used for the same purpose.

The server runs on Linux, because that allows us to collect
several kernel-level metrics (see below). We allow for
both native clients (e.g., `ndt7-client-go`) and browser clients
(e.g., `ndt7-js`). Broadly speaking, native clients have a
higher performance than browser clients, since the latter
are structurally constrained by the browser's multi-process
architecture and by the communication between the renderer
process (which runs JavaScript) and the network process.

The `ndt7` protocol uses WebSocket. The WebSocket protocol
is a web protocol that allows creating a bidirectional
data stream by upgrading an HTTP/1.1 connection.

The data stream contains both binary and text messages. Each
message carries its own type and payload.

In `ndt7`, the binary messages carry random data necessary to
create network load; the text messages carry metrics collected
by either party. The server uses text messages to deliver
data coming from three main data sources:

1. TCPInfo metrics obtained using `getsockopt`

2. BBRInfo metrics obtained using `getsockopt`

3. AppInfo metrics obtained by counting the I/O bytes

A native client (e.g., a client written in Go running on Linux)
could in principle collect and submit the same data. A client
that, instead, is using JavaScript, can only collect and submit
the AppInfo metrics, since the socket is not available.

It is important to remember that AppInfo at the receiver (the
client during download; the server during upload) is a good
quality data source. It counts the data actually received at
a given moment in time. This measurement excludes from the byte
counting the IP, TCP, TLS, and WebSocket overheads.

TCPInfo provides high-quality data in both directions. When
receiving, you get access to the received bytes at the TCP
level, along with a timestamp. When sending, you can rely on
the amount of acknowledged bytes. Both metrics allow one to
evaluate the transfer speed at TCP level.

One caveat applies to the sending side: the acknowledged
bytes are the bytes accepted by the TCP endpoint on the other
side, which is not necessarily the client. When a
TCP-terminating middlebox (e.g., a performance enhancing
proxy, see RFC 3135) splits the connection, that endpoint is
the middlebox. The acknowledged bytes then measure the path
up to the middlebox, whose buffer may absorb data faster
than the client receives it. Middleboxes were already noted in
2020 in [m-lab/ndt-server#238](https://github.com/m-lab/ndt-server/issues/238)
(open at the time of writing), which observes that the server
structure "does not behave well when there are
proxies/middleboxes".

Furthermore, the availability of TCPInfo and BBRInfo data
allows one to access diagnostic information that should
help understanding what was limiting the performance.

Broadly speaking, the main outstanding known limitations
of the ndt7 protocol are these:

1. the specification did not originally define a measurement
"zero": the current definition (the completion of the WebSocket
handshake) only appeared in v0.11.0 (February 2026), years
after implementations had been deployed. In any case, the two
parties observe the handshake completion at different moments,
so no shared zero exists, and how precisely a client observes
its own zero depends on the environment (compare a C client
controlling each operation with JavaScript receiving an
`onopen` event). Likewise, the start of byte counting is not
pinned to any event visible on the wire

2. WebSockets are known to behave differently in different
browsers and are anyway subject to the multi-process
constraints discussed above

3. piggybacking measurements as text messages causes delays
in delivering measurements to the other party, since
a piece of measurement is queued after all the other binary
messages that have already been queued at a given time
(the specification has warned about this queuing delay since
2019; [m-lab/ndt-server#378](https://github.com/m-lab/ndt-server/issues/378),
open at the time of writing, relates it to the 1 MB maximum
binary message size)

4. the protocol termination is loosely specified: closing
the connection after thirteen seconds is a MAY, closing it
immediately afterwards is only an ideal SHOULD, and the
client SHOULD wait for the server to close the underlying
TLS connection. Empirically, this looseness combines with
implementation issues (e.g., JavaScript timers) such that
the overall duration of tests is not guaranteed to be
near 10 seconds

5. the `ndt-server` implementation, in particular, stops
collecting TCPInfo/BBRInfo data when the socket is
waiting to become writable (documented in
[m-lab/ndt-server#238](https://github.com/m-lab/ndt-server/issues/238)
and [m-lab/ndt-server#378](https://github.com/m-lab/ndt-server/issues/378),
both open at the time of writing)

The latter issue, however, is mitigated by the existence
of the `m-lab/tcp-info` sidecar, which polls the kernel
every 10 ms independently of `ndt-server`.

Two caveats apply to the archived sidecar data. First, the
sidecar records a snapshot only when it differs from the
previous one, so a fully stalled connection produces gaps.
Second, the M-Lab pipeline keeps only every tenth recorded
snapshot, always preserving the last one. In our data, the
median inter-snapshot spacing is about 250 ms, and the
timestamp of the last snapshot lands near the end of the
life of the TCP endpoint in the kernel.

## The `ndt7-js` client

Since `giga-meter` uses `ndt7-js@0.0.6`, it is worth
describing how this client runs the download test and what
it reports at the end.

The test runs inside a Web Worker, which opens the WebSocket.
Inside `onopen`, the worker resets its clock (`performance.now`)
and its byte count, so the connection setup is excluded from
the client-side elapsed time. The zero still lags the on-wire
handshake completion by an unknown event-loop scheduling delay.

The worker emits a client-side measurement (`ElapsedTime` and
`NumBytes`) only when it processes a WebSocket message event
(`onmessage`) and more than 250 ms have passed since the
previous measurement. There is no timer. Hence, the last
measurement tracks (within 250 ms) the last message event the
worker processed, and the client-side elapsed time stops advancing
when the worker stops processing messages, either because
messages stop arriving (e.g., during a stall) or because the
worker itself is not running. Note that the worker reads the
clock when the event is dispatched, not when the data reaches
the host, so the elapsed time includes any dispatch delay.
The worker also forwards every server text message to the
main thread.

The main thread remembers the latest client measurement and
the latest server measurement. When the worker is resolved
successfully, the main thread invokes the "complete" callback
with both (`LastClientMeasurement` and `LastServerMeasurement`)
and terminates the worker. This is what `giga-meter` stores.

The worker is resolved successfully either when the WebSocket
closes or when a 12 second timer fires, whichever comes first.
Hence, a test cut by the timer is reported as a success, and
its last measurements are stored as such. When the WebSocket
reports an error, instead, the worker is resolved with an
error code and "complete" is not invoked. The timer
starts when the worker is created, before the client waits
for the server URLs and before the worker opens the WebSocket.
Therefore, the 12 second budget includes the connection setup
(TCP, TLS, and WebSocket handshakes) as well as the test.
When everything before `onopen` takes more than 2 seconds
(e.g., on high-latency paths), this leaves less than 10
seconds for the test itself. This bug was fixed by
[m-lab/ndt7-js#111](https://github.com/m-lab/ndt7-js/pull/111)
(released in `0.1.5`), which starts the 12 second timer when
the worker reports `onopen`. The `giga-meter` version we
consider still vendors `0.0.6`.
