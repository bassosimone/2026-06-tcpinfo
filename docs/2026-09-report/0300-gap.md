# Duration Gap Metric

> This document discusses the duration gap metric.

The duration gap is the difference, at the T3 level, between
the test duration according to data produced by `giga-meter`
and the duration according to data that `ndt-server` relayed
to the client.

We define the metric at the T3 level because T3 is the only
data available to Giga (through Superset), and it is in this
data that Giga observed tests running for a very long time,
which motivates the original research question (see
[the research questions](0100-rqs.md)).

This is the precise definition of the metric gap:

    gap_s = t3_client_elapsed_time - t3_tcp_ElapsedTime / 1e06

where:

1. `t3_client_elapsed_time` is the `ElapsedTime` of the last
client measurement stored by `giga-meter`, measured from
the `onopen` event in the download worker to the dispatch
of the last message event that triggered a client measurement; it
stops advancing when the worker stops processing messages (see
[the ndt7 document](0000-ndt7.md) for how `ndt7-js`
produces this value)

2. `t3_tcp_ElapsedTime` is the `ElapsedTime` of the TCPInfo
snapshot in the last server measurement stored by
`giga-meter`. It lives in the past because of latency, of
head-of-line blocking behind binary messages, and of `ndt-server`
pausing its sampling while the socket is not writable (see
[the ndt7 document](0000-ndt7.md)). Its zero is the
moment `ndt-server` starts its measurement loop, shortly
after the WebSocket upgrade completes.

Note that `t3_client_elapsed_time` is also influenced by the
12 second timer of `ndt7-js@0.0.6`, whose budget includes the
connection setup (see [the ndt7 document](0000-ndt7.md)).

As a result, we can formulate the following empirical model:

1. if `t3_client_elapsed_time << 10s`, possible causes are:
(a) the connection setup significantly reduces the overall
12 seconds budget; (b) a stall, during which the worker
processes no messages (because none arrive or because the
worker is not running/suspended) and the client-side elapsed
time stops advancing; (c) the server closing the connection
early (e.g., because of early exit, which, however,
`giga-meter` does not request)

2. if `t3_client_elapsed_time >> 12s`, the 12 seconds timer
callback must have run late on the main thread, since a timer
firing on time bounds `t3_client_elapsed_time` to 12 seconds
minus the connection setup

To determine who closed the connection first, we can observe
the first non-`ESTABLISHED` state published by the sidecar and
make the following simplifying assumption: if the server
closed the connection first, its state would be `FIN_WAIT1`,
otherwise `CLOSE_WAIT`.

Knowing this, we can now produce a table that compares:

1. the first non-`ESTABLISHED` state

2. the `t3_client_elapsed_time`

The table itself is generated by `make gap_distribution` and folds
together subsequent states in the state machine (the ETL pipeline
implements samples thinning, and a given state is transient anyway,
so we adopt a slightly more robust approach here, but the basic
substance of what we're checking for does not change):

The main take away is that the client closes the connection first or the
socket vanishes (last state being `ESTABLISHED`; probably abrupt end with
the connection being `RST`) in most cases when we are below 9.5 seconds
of duration. The longer the test runs, the more likely it is that the
server is closing the connection.

This interpretation supports the hypothesis that the unified 12 seconds
budget for preparing for the test (invoking locate, setting up the
WebSocket, etc) was a real bug (fixed upstream but not included
by the `giga-meter` version using for this analysis), and was
responsible for the observed shorter-than-expected tests.

The running-for-longer-than-expected cases remain unexplained after
analyzing this table. However, before looking more deeply into this
case, let us show what happens in `tcp-info` for a short test, to
ground the above table into actual, per-connection data.

From reading the `ndt-server` source code, we know that BBR is
enabled by the `measurer` component after the WebSocket connection
has been established. We do not know whether sample thinning in
the ETL dropped samples, yet, what we can say for sure is that BBR
was enabled within the [0-4.154] second window. When was BBR
actually set up? How much did the connection setup last?

test: it happens 3.3 seconds after the connection establishment,
therefore, we know that 3.3 seconds of budget were consumed
creating the WebSocket and that our `tcp-info` sample is ~0.85
second past that. In a typical TLS handshake with an M-Lab
server, the client writes approximately 1.5k bytes and receives
5.5k bytes (measured with [sonda][sonda]). Hence, the sample
is some 10k bytes past the end of the TLS handshake.

[sonda]: https://github.com/bassosimone/sonda

Lastly, the `FIN` from the client reaches the server between
samples indexes 13 and 14, thus approximately ~9.2 seconds after the
connection was accepted. Assuming a 12 second budget, this means
that the following is most likely true:

1. the test lasted ~6 seconds

2. the WebSocket establishment lasted ~3 seconds

3. the call to locate lasted ~3 seconds

Performance-wise, the delivery rate is at ~1 Mbit/s.

In conclusion, the available data strongly show how the 12
second budget could limit the overall test duration when the
RTT is high and/or the available bandwidth is low.

## Duration by tier

The previous case study illustrated how it is possible
for the client-side and the server-side duration of a
test to disagree. We also deferred explaining tests whose
client-side duration exceeds the expected maximum time
of 12 seconds. Now, it is time to circle back to such a
problem. To start diving into it, we need to define
the test duration more precisely.

There are six distinct definition of duration:

1. `t2_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot collected by `ndt-server`. This is at most about
10 s (`spec.DefaultRuntime`), and possibly much earlier,
since `ndt-server` stops sampling while the socket is not
writable (see [the ndt7 document](0000-ndt7.md))

2. `t2_wall`: `ndt-server` wall clock, computed by
subtracting `StartTime` from `EndTime`. Both are taken by
the download sender, so this is how long the server kept
sending: about 10 s, plus any time a write stayed blocked
past 10 s, capped at about 15 s by the write deadline. It
excludes waiting for the client's Close reply.

3. `t1_est`: wall clock from T2's `StartTime` to the last
ESTABLISHED sidecar snapshot. `ndt-server` closes the socket
after the closing handshake completes (or at 15 s), so this
snapshot typically marks the server close; when the client
closes first (see `scripts/build_three_tier.py`), it marks
the client close instead. Because of the sidecar sampling
(see [the ndt7 document](0000-ndt7.md)), it may precede the
actual transition by a few hundred milliseconds.

4. `t1_any`: wall clock from T2's `StartTime` to the last
sidecar snapshot regardless of TCP state, i.e., near the end
of the life of the TCP endpoint in the kernel

5. `t3_client`: the elapsed time reported by the client
(`t3_client_elapsed_time` above)

6. `t3_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot stored by `giga-meter` (`t3_tcp_ElapsedTime` above)

Note that tier 1 does not export `ElapsedTime`. Since the
server and the sidecar share the same clock and `StartTime`
is roughly when we start sending, we can use that specific
time as the zero for tier 1 measurements.

These are the distributions produced by
`make gap_distribution` (window 2026-01-01 to 2026-08-01,
start included, end excluded; n=53,855; seconds). Note that
these tests likely under-represent high-latency paths and
long test durations (see [the data document](0200-data.md)):


Some minor observations, first:

2. `t2_kernel` shows what we observed above about short

3. `t3_kernel` shows that T3 data indeed may lag behind
T1 and T2 data (see the `p5` value)

4. `t2_wall` at `p99` shows ndt-server liveness bound: after 15s

Then, the two interesting data points:

the connection survives for at least five more seconds

2. Likewise, the `t3_client` with `16` seconds of `p99`
indicates that the 12-seconds worker timeout does not
always fire on time. This observation is complementary to
the one above and points out to an orthogonal direction
towards which to investigate: why is the `12` second worker
timeout not effective in some cases?

## Classification of long tests

We start by answering the first of the two questions. What is
the reason why the test runs long?

The analysis is limited to tests where the client reports
more than nine seconds of duration, since an explanation
already exists for short tests.

We divide the tests in three distinct classes. The aim is to
model why a test would run for longer than expected. There
are two possible reasons:

1. flow control forced the sender to pause

2. there is a large queue to drain

In reality, the split between those two classes is a
continuum and we define arbitrary thresholds to force
a binary split between them:

1. the `Z` class contains tests where the samples see the
window going to zero during the test

2. the `Q` class contains tests not in `Z` where the bytes
queued and in flight would take more than one second to
drain at the mean observed throughput

3. the `O` class contains the residual tests

Because the sidecar collapses equal entries and because the
ETL pipeline decimates the samples, this class actually
underestimates the occurrences of a zero window. In any case,
this measurement is reasonably robust: 81% of the tests
in the `Z` class have 1+ seconds of `RwndLimited` at close,
which is why we think it is OK to use it.

shows higher smoothed RTT statistics and higher backlog at close
than the two other classes. The `Z` class shows a RTT range partially
overlapping with the `O` class and this, intuitively, confirms that
the core reason for running for a long time for `Z` is an unexpected
stall rather than the queue. Also, `Z` connections have a higher
fraction of RWND-limited time than other connections.

In turn, the partially overlapping MinRTTs disprove the hypothesis of a PEP in
the middle splitting the path in two that only affects the `Z` class. In such
specific case, we would have expected to observe an unreasonably low RTT.

## Towards understanding the late timer

Now that we have discussed examples of long running tests, let
us track back and focus on the timer that fires late.

Before trying to investigate the issue, it is worth stating
what conditions produce an observable late timer:

1. standing queue (hence, in our model, `Q`) so that the
messages closing the WebSocket and the TLS connection are
delayed by the unsent and inflight data, or long stalls
that defer draining the queue (hence `Z`)

2. the timer itself firing late

As things stand and without instrumentation, we can only
detect cases in which (1) and (2) happen together.

That said, it is worth asking the question whether the way
in which the app runs influences the timer behavior. The
hypothesis here is that, when running in `manual` mode or
`startup` mode, the window is visible, while, for `daily`
mode (i.e. background tests) the window is not visible
*and* this fact has an impact on the timer.

For `manual` mode the window is visible for sure while for
`startup` mode we cannot be sure because the operator may
hide it. What we know is that the window is shown right
after logging into the system.

That is, we would expect the rate of `Q` and `Z` tests with
long runtimes in `manual` (and possibly `startup`) to be
far below the `daily` tests.

## Conclusion

- Tests with short runtimes depend on using the same 12 second
  watchdog timer to cover the query to `m-lab/locate`, the WebSocket
  connection establishment, and the test proper. The fix
  landed upstream in [m-lab/ndt7-js#111](https://github.com/m-lab/ndt7-js/pull/111)
  but is not included in the `giga-meter` tests analyzed in this report.

- Tests with very long runtimes happen because the 12 seconds
  timer fires much later than the scheduled 12 seconds, otherwise,
  they would be interrupted after 12 seconds

- The specific reason why the timer fires late does not seem to
  be related to the run mode (`manual` versus `daily` versus
  `startup`), and understanding it would probably require
  client instrumentation

- Tests with late timers are only visible when the amount of
  data scheduled to send by ndt7 far exceed the ability of the
  client to drain it, which happens in two conditions:

   - `Z`: the client pauses reading for significant amount of
     times, thus deferring draining the queue

   - `Q`: the queue (socket buffer plus network queue) created
     by ndt7 far exceeds the network available draining capacity,
     leading to very long drain times

- The original ndt7 design recommended using a 13 seconds timer
  to protect against unforeseen conditions and bound the overall
  runtime (see [0000-ndt7.md](0000-ndt7.md)), but, as things
  stand, we cannot trust this timer to fire reliably

- While `Z` is a specific condition that could relate to the
  presence of a PEP splitting the end-to-end path, the observed
  RTTs seem compatible with end-to-end connectivity
