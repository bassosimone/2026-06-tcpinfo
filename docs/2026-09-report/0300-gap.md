> This document discusses the duration gap metric.

The duration gap is the gap between the duration of a `ndt7`
test reported by `giga-meter` and the duration according
to `ndt-server` and the `tcpinfo` sidecar.

This is the precise definition of the metric gap:

    gap_s = t3_client_elapsed_time - t3_tcp_ElapsedTime / 1e06

where:

1. `t3_client_elapsed_time` is the elapsed time according to
the client, which is computed between the delivery of the
`onopen` event to the download worker (the worker resets its
clock and its byte count inside `onopen`, so the dial is
excluded; the zero still lags the on-wire handshake completion
by an unknown event-loop scheduling delay) and the latest event
observed by the client itself (the JavaScript client posts a
"complete" message at the end but does not include the
observed metrics, which means that the final event is whenever
the 250 millisecond timer has fired)

2. `t3_tcp_Elapsedtime` is the `ElapsedTime` in the latest
TCPInfo snapshot received by the client, which lives in the
past due to, at least, latency and uses as zero the moment
in which the WebSocket connection is ready

Because of these definitions, the client elapsed time is
a lower bound on the true window, where the true window
runs from the on-wire handshake completion to the last
data arrival at the client: the zero lags the handshake
by a scheduling delay, and the end is truncated to the
last measurement tick, normally by at most ~250 ms and
arbitrarily under stalls (see the zero-receive-window
family below). Conversely, the
server definition of the elapsed time is more robust
since the establishment of the WebSocket channel is
a discrete event plus some delay caused by goroutine
scheduling etc. However, there are doubts about
whether `ndt-server` collects a "final" event when
it is closing the connection or whether this is
a scheduled event depending on a timer. Also, there
are delays entailed by this as we said above.

## Duration by tier

To put the gap in context, we measured the test duration
as seen by each tier. We use six measures:

1. `t2_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot collected by `ndt-server` (the measurement stop)

2. `t2_wall`: `ndt-server` wall clock, from `StartTime`
to `EndTime`

3. `t1_est`: wall clock from T2's `StartTime` to the last
ESTABLISHED sidecar snapshot, which empirically marks the
moment the server closes the connection (see below)

4. `t1_any`: wall clock from T2's `StartTime` to the last
sidecar snapshot regardless of TCP state, i.e., near the end
of the life of the TCP endpoint in the kernel

5. `t3_client`: the elapsed time reported by the client
(`t3_client_elapsed_time` above)

6. `t3_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot the client received (`t3_tcp_ElapsedTime` above)

The `t1_*` measures are wall-clock differences because the
sidecar does not export a kernel `ElapsedTime`; the
construction lives in `scripts/build_three_tier.py`.

These are the distributions produced by
`make gap_distribution` (window 2026-01-01 to 2026-08-01,
n=53,855; seconds):

Three observations. First, the kernel measures clamp at ten
seconds, as expected: the measurement stops there. Second,
everything else happens after the measurement stop: the
server closes the connection a median 0.6 s later
(`t1_est - t2_kernel`) and the TCP endpoint survives even
longer (`t1_any`). Third, the sidecar record outlives the
client's reported end in at least 95% of tests
(`t1_any - t3_client` is +0.05 s at p5): the sidecar tracks
the connection for as long as the client runs, and then some.

    MW  (n=18,093):  p50 +1.644  p90 +6.179   >1s 64.0%   <=0 3.3%
    Per-school medians (>=10 tests): MD -0.09 to +4.03 s (80 schools),
                                     MW -0.05 to +6.78 s (101 schools)

The gap is positive nearly everywhere, larger in Malawi than
in Moldova, and heterogeneous across schools. The rest of
this document explains where the tail comes from.

## The long tail: force-close and queue drain

`ndt-server` force-closes the connection when the handler
context expires after 15 s of wall-clock time
(`spec.MaxRuntime = 15 * time.Second` in `ndt7/spec/spec.go`
line 65, enforced in `ndt7/handler/handler.go` line 94; tag
`v0.25.1`). Consistently, `t2_wall` clamps at exactly
15.000 s at p99 in the table above.

Closing the socket does not make the queued data disappear.
On a bufferbloated path, the bytes already accepted by the
kernel (and by any buffer along the path) keep flowing toward
the client while the endpoint sits in FIN_WAIT1. The client
keeps receiving data, keeps counting elapsed time, and has no
way to know the server already closed. The sidecar observes
all of this from the kernel.

A worked example, produced by
`uv run scripts/dump_test_snapshots.py --uuid
ndt-74vlv_1777680611_00000000000A706F` (a Malawi test from
2026-05-11 whose client reported 100.70 s; rows trimmed,
`t_s` is relative to the first sidecar snapshot):

Reading the timeline: about 1.2 MB enters the socket in the
first second; the RTT inflates from 46 ms to 10.7 s (extreme
bufferbloat); the server force-closes at 15 s and the sidecar
sees FIN_WAIT1 at 15.55 s; the queue then drains for 85 s,
with `BytesAcked` creeping from 1.20 MB to 1.57 MB and a
4,380-byte retransmission burst; the final snapshot lands
just after the client's reported end (for this test,
`t1_any - t3_client` = +0.13 s), with the RTT back to 58 ms
because the queue is finally empty. The client counted
all of the drain as test time. Note that the sidecar timeline
is sparse and has multi-second recording gaps during stalls,
for the reasons discussed in `0000-ndt7.md`.

As a side effect, `ndt-server` itself measured almost
nothing here: it collected two TCPInfo samples and a kernel
elapsed time of 0.83 s, because its collection loop stops
while the socket is not writable (again `0000-ndt7.md`).

## Corner-case selectors and a second family

To size this phenomenon we used two selectors, both printed
by `make gap_distribution`:

    Corner cases, selector A (t3_client > 15 s): 820/53,855 tests (1.52%)
    Corner cases, selector B (last state FIN_WAIT1, drain > 5 s): 508/53,855 tests (0.94%)
    Overlap: A&B 351  A only 469  B only 157

Selector A cuts on the symptom: the client reports a duration
beyond the server's own 15 s limit. Selector B cuts on the
mechanism: the last sidecar snapshot is FIN_WAIT1 and the
drain (`t1_any - t1_est`) exceeds 5 s. Both thresholds are
arbitrary cuts through continuous distributions, and neither
selector subsumes the other.

We grounded the disagreement by dumping one
median-representative test from each side:

1. A-only (`ndt-sldj8_1777653684_00000000001313C8`, MW,
client reported 16.39 s): the same force-close-plus-drain
mechanism, with a 4.58 s drain that misses B's 5 s cut. Part
of the A-only population is therefore a threshold artifact.

2. B-only (`ndt-virtual-2xfr6_1777769998_000000000005AB88`,
MD, client reported 8.70 s): a different mechanism, a zero
receive window stall. The test moves 23 MB in 4.6 s, then the
client stops reading: the send window collapses to zero,
`tcp_RWndLimited` grows to 18.3 s, and 3.7 MB of queued data
is never sent. The server force-closes at 15 s, the endpoint
lingers in FIN_WAIT1 until 20.3 s, and the client reports
only 8.70 s. In this family the client under-reports the
endpoint lifetime, which also shows up as the negative tail
of `t1_any - t3_client` within selector A (p5 = -4.7 s).

So the drain mechanism explains the extreme positive tail of
the gap, but the corner-case population is mixed: it also
contains milder drains below any given threshold and
client-side stalls where the reported duration is too short
rather than too long. A systematic classification of
termination behaviors is possible future work; we did not
pursue it here because no current analysis depends on the
composition of this 1.5% of tests.

Beyond bounding the tail, the drain observation has a
positive reading: a multi-second drain after the server
closes is direct evidence of buffering on the path, which is
itself a quality signal the sidecar captures and the client
cannot.

## Reproducing

The analysis assumes the per-snapshot and per-test parquet
files are already in `data/`. The top-level `README.md`
documents how to fetch the raw data and build them
(`make export_mlab_data` plus the Superset CSV exports, then
`make build_ndt7_download`, `make build_tcpinfo`, and
`make build_superset_download`).

From there, two commands reproduce every population statistic
quoted in this document:

    make build_three_tier
    make gap_distribution

The first joins the three tiers into
`data/three_tier_20260101_20260801.parquet` (the default
window matches the one used here). The second prints the
duration tables, the gap distribution, and the corner-case
selector statistics.

The per-test timelines come from:

    uv run scripts/dump_test_snapshots.py --uuid <uuid>

using the three UUIDs quoted above. This reads the weekly
`data/tcpinfo_*.parquet` files directly and does not need
the three-tier join.
