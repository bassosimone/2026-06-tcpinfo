# Duration Gap Metric

> This document discusses the duration gap metric.

The duration gap is the difference, at the T3 level, between
the test duration according to data produced by `giga-meter`
and the duration according to data that `ndt-server` relayed
to the client.

We define the metric at the T3 level because T3 is the only
data available to Giga (through Superset), and it is in this
data that Giga observed tests running for a very long time,
which motivates the original research question (see
[the research questions](0100-rqs.md)).

This is the precise definition of the metric gap:

    gap_s = t3_client_elapsed_time - t3_tcp_ElapsedTime / 1e06

where:

1. `t3_client_elapsed_time` is the `ElapsedTime` of the last
client measurement stored by `giga-meter`, measured from the
`onopen` event in the download worker to the dispatch of the
last message event that triggered a client measurement; it
stops advancing when the worker stops processing messages (see
[the ndt7 document](0000-ndt7.md) for how `ndt7-js`
produces this value)

2. `t3_tcp_ElapsedTime` is the `ElapsedTime` of the TCPInfo
snapshot in the last server measurement stored by `giga-meter`.
It lives in the past because of latency, of head-of-line
blocking behind binary messages, and of `ndt-server` pausing
its sampling while the socket is not writable (see
[the ndt7 document](0000-ndt7.md)). Its zero is the moment
`ndt-server` starts its measurement loop, shortly after the
WebSocket upgrade completes.

Note that `t3_client_elapsed_time` is also influenced by the
12 second timer of `ndt7-js@0.0.6`, whose budget includes the
connection setup (see [the ndt7 document](0000-ndt7.md)).

As a result, we can formulate the following empirical model:

1. if `t3_client_elapsed_time << 10s`, possible causes are:
(a) the connection setup significantly reduces the overall
12 seconds budget; (b) a stall, during which the worker
processes no messages (because none arrive or because the
worker is not running) and the client-side elapsed time stops
advancing;
(c) the server closing the connection early (e.g., because
of early exit, which, however, `giga-meter` does not request)

2. if `t3_client_elapsed_time >> 12s`, the 12 seconds timer
callback must have run late on the main thread, since a timer
firing on time bounds `t3_client_elapsed_time` to 12 seconds
minus the connection setup

Both terms of the gap are therefore imperfect: the client
term depends on when the worker processes messages and on
the timer, and the server term is stale by the time the
client stores it. We
can use the data collected at T2 (`ndt-server`) and T1 (the
`tcp-info` sidecar), which does not travel through the
WebSocket, to characterize what happens on each side.

## Duration by tier

We define six distinct measurements of time:

1. `t2_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot collected by `ndt-server`. This is at most about
10 s (`spec.DefaultRuntime`), and possibly much earlier,
since `ndt-server` stops sampling while the socket is not
writable (see [the ndt7 document](0000-ndt7.md))

2. `t2_wall`: `ndt-server` wall clock, computed by
subtracting `StartTime` from `EndTime`. Both are taken by
the download sender, so this is how long the server kept
sending: about 10 s, plus any time a write stayed blocked
past 10 s, capped at about 15 s by the write deadline. It
excludes waiting for the client's Close reply.

3. `t1_est`: wall clock from T2's `StartTime` to the last
ESTABLISHED sidecar snapshot. `ndt-server` closes the socket
after the closing handshake completes (or at 15 s), so this
snapshot typically marks the server close; when the client
closes first (see `scripts/build_three_tier.py`), it marks
the client close instead. Because of the sidecar sampling
(see [the ndt7 document](0000-ndt7.md)), it may precede the
actual transition by a few hundred milliseconds.

4. `t1_any`: wall clock from T2's `StartTime` to the last
sidecar snapshot regardless of TCP state, i.e., near the end
of the life of the TCP endpoint in the kernel

5. `t3_client`: the elapsed time reported by the client
(`t3_client_elapsed_time` above)

6. `t3_kernel`: the kernel `ElapsedTime` in the last TCPInfo
snapshot stored by `giga-meter` (`t3_tcp_ElapsedTime` above)

Note that tier 1 does not export `ElapsedTime`. Since the
server and the sidecar share the same clock and `StartTime`
is roughly when we start sending, we can use that specific
time as the zero for tier 1 measurements.

## Case study: a 100 second test

As discussed in observations 3 and 4, `ndt-server` closes
the socket at about 15 s at the latest.

Closing the socket does not make the queued data disappear.
On a bufferbloated path, the bytes already accepted by the
kernel (and by any buffer along the path) keep flowing towards
the client while the endpoint sits in `FIN_WAIT1`. The client
keeps receiving data and has no way to know that the server
already closed until the queued data has been delivered. If,
in addition, the 12 s timer fires late (see observation 7),
the client keeps updating its elapsed time throughout the
drain. The sidecar observes the drain from the kernel.

The `rtt_ms` column (the kernel smoothed RTT) grows from
40 ms at the start to 10.7 s at 35.3 s. Over the whole test,
the endpoint delivers about 1.57 MB (about 125 kbit/s), yet
between 1.2 and 8.9 seconds it keeps about 90 packets in

`13` shows a `ProbeBW (drain)` with the `0.75` `pacing_gain`

The congestion window is only one of the limits on how much
data the sender can keep in flight. The sender also cannot
exceed the window advertised by the receiver (`SndWnd`), and
it cannot send data the application has not written yet. The
kernel accounts for these conditions with cumulative
counters: the time during which the send queue was not empty
(`busy_ms`), and the portions of that time during which
sending was limited by the receive window (`rwnd_lim_ms`) or
by the send buffer (`sndbuf_lim_ms`). Because these are
counters, the difference between two rows is exact even
though the timeline is sparse.

To size this phenomenon we used two selectors, both printed
by `make gap_distribution`:

    Corner cases, selector A (t3_client > 15 s): 820/53,855 tests (1.52%)
    Corner cases, selector B (last state FIN_WAIT1, drain > 5 s): 508/53,855 tests (0.94%)
    Overlap: A&B 351  A only 469  B only 157

Selector A cuts on the symptom: the client reports a duration
beyond the server's own 15 s limit. Selector B cuts on the
mechanism: the last sidecar snapshot is FIN_WAIT1 and the
drain (`t1_any - t1_est`) exceeds 5 s. Both thresholds are
arbitrary cuts through continuous distributions, and neither
selector subsumes the other.

We grounded the disagreement by dumping one
median-representative test from each side:

1. A-only (`ndt-sldj8_1777653684_00000000001313C8`, MW,
client reported 16.39 s): the same force-close-plus-drain
mechanism, with a 4.58 s drain that misses B's 5 s cut. Part
of the A-only population is therefore a threshold artifact.

2. B-only (`ndt-virtual-2xfr6_1777769998_000000000005AB88`,
MD, client reported 8.70 s): a different mechanism, a zero
receive window stall. The test moves 23 MB in 4.6 s, then the
client stops reading: the send window collapses to zero,
`tcp_RWndLimited` grows to 18.3 s, and 3.7 MB of queued data
is never sent. The server force-closes at 15 s, the endpoint
lingers in FIN_WAIT1 until 20.3 s, and the client reports
only 8.70 s. In this family the client under-reports the
endpoint lifetime, which also shows up as the negative tail
of `t1_any - t3_client` within selector A (p5 = -4.7 s).

So the drain mechanism explains the extreme positive tail of
the gap, but the corner-case population is mixed: it also
contains milder drains below any given threshold and
client-side stalls where the reported duration is too short
rather than too long. A systematic classification of
termination behaviors is possible future work; we did not
pursue it here because no current analysis depends on the
composition of this 1.5% of tests.
